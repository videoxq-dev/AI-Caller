# Booking follow-up: September 22, 2026

## Failure identified

The attached deployment log shows migrations 0025–0030 applied, followed by legacy orchestration repair warnings. The screenshot's `Available times include ... Which would you like to book?` response is generated by the legacy orchestrator, not the durable booking preview renderer.

The implementation installed the new engine but required both `AI_CALLER_BOOKING_V2=enabled` and a per-workspace `BOOKING_ENGINE_VERSION=v2` entitlement. Neither environment example explained that requirement. Widget sessions were pinned to v1 for up to 30 days. Redeploying the new code and migrations therefore did not make normal customers use the remediation.

Additional failures reproduced through the authenticated widget route and real PostgreSQL:

- Repeating `yes` or asking `is it booked?` after success lost the completed draft and fell through to the legacy planner.
- Repeating a preview after a side question omitted preview metadata/delivery evidence, so the next yes could not confirm it.
- Null optional extraction fields rejected otherwise usable messages.
- Range offers had no intent for selecting an opaque offer ID. The draft did not adopt the selected offer's local date/time.
- The default timezone was used for availability but not persisted as conversation state.

## Changes

- Durable booking is the default for new sessions. `disabled` explicitly rolls back new sessions, and `opt-in` retains the original two-gate rollout. A workspace explicitly marked v1 stays on v1.
- Existing v1 widgets switch on a fresh request such as `I want to book a cleaning service`. Old approvals do not switch engines. Unconfirmed legacy booking previews are superseded; an authorized unresolved legacy action or another processing turn prevents handoff.
- The widget logs the selected engine version with workspace/conversation/session identifiers, without customer text.
- Completed receipts answer repeated approval/status messages directly. In-flight commands remain reachable beyond draft collection expiry.
- Repeating a preview rechecks availability and creates a new offer/version/preview with fresh delivery evidence, preserving database uniqueness and invalidating old controls.
- Optional nulls are treated as omitted extraction fields. Date/time clarification errors remain recoverable rather than automatically raising staff issues.
- The extractor can select an offered ID. Ambiguous yes after multiple offers asks which one; a single-offer yes prepares a preview, which still requires approval. Selection stores the offer's date/time/timezone on the draft.
- The browser acceptance scenario now checks ordinary default rollout, split date/time messages, Lagos local time, four-hour persistence, confirmation, retry, status lookup, refresh, and session isolation. Its fixture no longer invents UTC for a bare 11 AM.
- Vitest excludes generated `.next` copies of source tests, so running tests after a production build does not collect duplicate/stale test files.

## Deployment

No additional migration is required beyond the already applied 0025–0030 migrations. Rebuild and redeploy web, worker, and gateway from this revision together.

Use `AI_CALLER_BOOKING_V2=enabled` (also the unset default). Remove an unintended explicit workspace v1 override if present; preserve intentional rollback assignments. Existing v2 sessions and commands keep their engine during rollback.

For an existing failed widget conversation, start a fresh request: `I want to book a cleaning service`. This safely changes eligible v1 sessions to v2. A new widget session also starts on v2. Do not try to approve an old unconfirmed preview as a way to migrate it.

Verify the business timezone is the one actually intended; the customer's location alone does not establish a timezone.
